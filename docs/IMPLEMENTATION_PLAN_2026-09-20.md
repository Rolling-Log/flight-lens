# Flight Lens：从列表比价到真实全价的实施计划

日期：2026-09-20。依据：[本轮实测与代码审计](PROJECT_AUDIT_2026-09-20.md)。
本文是后续设计与验收要求，不表示这些能力已经上线。阶段按验收推进，不把未知的平台接入工作写成确定交付日期。

> 优先级已按用户最新反馈调整：以 [搜索底层重构评估](SEARCH_FOUNDATION_REVIEW_2026-09-20.md) 为准。
> 先解决低价候选漏检、接口覆盖与搜索失败恢复；本文的报价/费用模型作为后续比较与复核要求保留。

## 1. 产品决策

保留现有液态玻璃 UI、Next.js / Fastify 和 monorepo，重做报价模型、采集编排与核价闭环。
现阶段的大部分价值来自拿到可信的商品与费用明细；全面换框架或继续堆动效不能解决这一点。

目标是：**在用户接受的日期、机场、行李和退改条件内，找到本次已核验渠道中实际可继续购买的最低应付金额，并明确还有哪些渠道没有核验。**
全网各平台最低价是长期覆盖目标，不能成为当前结果的无条件宣传。平台数量、返回条数和抓到的最小数字都不是完成标准。

首个可用范围固定为中国内地单程、1 位成人、经济舱、精确机场、直飞；先选择两个航司的样本。
多成人、转机、往返和附近机场保留现有入口，但必须显示其实际核验能力，不能继承单成人直飞的验收结论。

### 为什么先做费用明细

本轮携程 HU7601 样本，列表 ¥550，零额外服务的填写页显示票价 ¥550 + 机建 ¥50 + 燃油 ¥70 = ¥670；
同航班还有 +¥48 服务包等产品。当前聚合得到的来源详情最低价曾为 ¥720。
这证明：只增加列表来源，会增加数字；展开正确的运价产品，才可能得到真正更低且条件合适的候选。
¥670 是一次人工填写页观察，尚未自动采集，也不是支付成交证明。

## 2. 报价必须成为有证据的商品

报价的唯一性不能只有“航班 + 卖家”。需要区分完整航段、实际承运人/共享航班、舱位、运价产品、行李、退改、人数、销售渠道与优惠资格。
以下为目标模型，沿现有 contracts / domain 逐步迁移，采用兼容字段与适配层，避免一次推倒 API。

| 信息 | 必需内容与规则 |
| --- | --- |
| 行程 | 每段出到达机场、当地日期时间、时区、跨日、班号、联程/分开出票；来源缺失不能用用户输入补成已匹配 |
| 商品 | source、seller、fareProductId/稳定指纹、舱等/运价品牌、库存观察、退改规则、精确商品或结果页跳转 |
| 旅客 | 类型、人数、每人/每段/整单的费用适用范围；当前成人模型先保持兼容 |
| 费用 | 票价、机建、燃油、其他税费、必选服务、满足要求的行李、已验证的即时优惠；全部用整数分 |
| 金额状态 | 每项为已观察、规则估算、明确不适用或未知；未知是 null/显式状态，禁止转成 0 |
| 总额 | 标注币种、每人/整单、包含项、缺失项；来源合并税费不能伪拆成机建和燃油，更不能重复相加 |
| 用户条件 | 公开价/本人的登录态价、平台会员、新客、银行卡/App 限制；未证实资格的优惠单独展示 |
| 证据 | 观察阶段、来源类型、采集器版本、时间、最小必要证据引用；客户端观察与服务端复核分开 |
| 时效 | 抓取时间、来源有效期或本系统复核期限、是否缓存、最近复核结果与变价原因 |

统一计算式：整单票价 + 全部必付税费 + 必选服务 + 用户要求的行李费用 − 确认适用的即时优惠。
返现、积分和不保证到账的权益单列。展示“额外买行李以后更贵”的差异，不能仅用票面价判断哪张票合适。

### 证据状态与信任边界

| 阶段 | 能说明什么 | 是否参与默认最低价 |
| --- | --- | --- |
| 列表线索 | 平台列表出现过某金额 | 否，进入“待核价候选” |
| 规则估算 | 对未知费用应用有版本且适用范围明确的规则 | 否，只帮助决定先核哪一张 |
| 来源明细 | 同一商品的必付费用完整、金额等式成立 | 可以，明确“来源明细价”与采集时间 |
| 购买前复核 | 相同行程/人数/商品在进入购买流程前再次确认金额和库存 | 优先，仍提示最终以平台确认为准 |
| 已变价/不可售/过期 | 复核失败或条件发生变化 | 退出最低价候选，保留原因与新价 |

“字段和总金额校验通过”不等于“平台真实性已经认证”。Edge Companion 的数据由客户端提供，
即使结构完整也不能自动变成所有用户共享的权威行情。保留 browser_observation 等来源类型，
个人结果按会话隔离；公共最低价与公共价格历史只接收满足相应服务端来源校验政策的记录。
不保存或上传平台密码、Cookie、乘机人信息、带令牌的完整购买 URL；证据先脱敏，设置保留期限。

## 3. 获取价格的两条路径

**云端公开来源**：可稳定使用且已获授权的数据接口/合作接口，以及现有 FlyAI、SerpApi。
每个来源先声明支持的市场、人数、行程、费用层级、跳转能力与调用成本，不支持的条件要在调度前跳过并解释。

**本人的浏览器来源**：通过 Edge Companion 使用用户已经登录的平台会话，读取本人可见的运价产品和费用。
登录、验证和平台阻断交回用户处理；云端账户登录不应显示成“携程已登录”。用户不装扩展时仍能使用公开来源，但个人价格覆盖需要明确提示。
先让 Edge 版形成稳定闭环；手机版的完整个人平台覆盖需另外验证可行入口，不能把桌面扩展当成手机可用方案。

云端长期运行的编排、缓存、预算与审计留在 API/任务层；Netlify 负责页面与同域代理。
长时间的平台浏览器任务不塞进网页请求中的短生命周期函数。现阶段不新建一套微服务。

### 一次查询的目标流程

1. 校验用户条件并固定 queryId；列表开始前给出本次计划覆盖的来源及不支持项。
2. 云端与本机独立采集并行运行；按来源逐步返回状态与候选，支持取消、截止时间和失败重试。
3. 保存原始报价的规范化快照；先检查机场、日期、人数和资格，再做商品去重。
4. 优先展开最有希望的 3～5 个候选，并为不同独立来源保留探测机会，避免只核第一个平台。
5. 补齐费用、行李和产品条件，形成可比较全价；若待核价线索仍可能更低，继续核价直到达到预算或截止时间。
6. 按完整应付金额排序；“合适”通过用户明确的时间、行李和退改偏好解释，不用不透明的模型权重掩盖价格。
7. 用户点击前重验该具体产品；有变价先更新金额并提示，再交接原平台购买。系统不自动提交订单。
8. 记录本次来源覆盖、未核候选、价差、时间和成本；失败不能记录成无票。

3～5 个候选是起始预算，不是全局最低价证明。只有确定的下界才能用于剪枝；若优惠可能降低金额、费用或商品范围未知，
就不能简单以“票面价高于当前全价”排除候选。超过预算时如实结束为部分覆盖，不假装穷举。

## 4. 具体实施顺序

### M0：线上与本地使用同一版本

- 修正 Netlify Production branch、Render Blueprint 和 API 服务分支；把发布目录和 API 分支写入版本配置。
- 每次发布记录网页 Deploy SHA 与 API health revision；检查解析、来源弹窗、查询、账户会话和移动布局。
- 下一步增加 CI 通过后的发布门禁、部署完成后的自动冒烟、前后端契约兼容检查和可见版本信息。
- 定位 Windows `next dev` 路由初始化错误；生产预览可用不能代替开发模式修复。
- 验证 Render 代理身份与限流：只信任实际边界；未完成前保留保守配置，并承认多用户可能共享限流配额。
- Netlify 中还保留旧架构的数据库/供应商环境变量。后续核对没有运行时依赖后清理，不能直接删除仍可能用于回滚的配置。

验收：一次真实 `main` 推送自动出现新 Netlify Published 部署；API 对应版本上线；线上核心交互可用。
部署成功与最低价功能达标分别验收。

### M1：携程单来源完整闭环（第一开发里程碑）

先做 6 个可独立审核的变更：

| 顺序 | 工作与落点 | 验收证据 |
| --- | --- | --- |
| 1 | contracts 增加费用完整性、商品指纹、观察阶段、用户范围；旧字段兼容映射 | 缺税费、明确零、合并税、多人/多航段、未知必选费和小数金额回放用例 |
| 2 | Companion 枚举携程同航班多个产品，区分零服务产品与套餐 | 不再只保留一个候选；同航班 +¥0 与 +¥48 不能去重合并 |
| 3 | 读取商品详情与无乘机人信息的费用展示；精确匹配航班/日期/舱位 | 捕获票价、机建和燃油；读不到时保留未知。若页面必须先填个人信息，则停在用户交接处 |
| 4 | domain 统一总额、资格和比较政策；候选采集与核价分离 | 机场错配、缺费、资格不明不能获最低全价徽标；客户端证据不可污染公共历史 |
| 5 | Web 分开“已获得完整全价”和“可能更低、待核价”，展示分项与更新时间 | ¥550 列表线索不再盖过 ¥670 全价；可明确看见未核候选与服务包差异 |
| 6 | 点击前复核、变价/无票处理、具体产品交接 | 至少完成金额未变、涨价、降价、无票、产品改变、需登录、超时 7 类路径 |

页面改版服务于价格可信度：先修文案与信息层级，再统一弹窗基础组件与动效。
玻璃效果保留，支持减少动态效果；大列表按实际性能测量决定分页或虚拟化。

验收先用不少于 10 次本人登录态实测，加脱敏回放覆盖异常；再进入 M2 的多来源样本。
HU7601 ¥670 用作历史结构示例，未来测试不得要求实时价格永远等于此数字。

### M2：做到可重复的多来源比价

- 飞猪先核实 FlyAI 返回能力：若只有列表价，就保留线索角色，接续本人页面核价，不能把它包装成完整报价接口。
- 接入一个航司直营作为独立核价基准，依据真实样本与可持续接入方式选择；第二个独立库存来源验证前不宣称跨平台闭环完成。
- 建立 20 条精确机场航线矩阵，覆盖短/长距离、同城多机场、临近/较远日期、工作日/周末、红眼与不同运价产品。
- 执行至少 50 次“同商品、同人数、短时间间隔”的成对核价；记录成功、失败、遗漏与变价，而非只记录抓到的样本。
- 机建/燃油规则库只做有依据的估算辅助：携带航司、出票生效时间、旅客类型、航段与豁免条件；来源明细优先。

阶段门槛：观察到的同商品金额匹配率目标 ≥95%，所有金额按分校验；缺失税费误记为 0 必须为 0；
返回失败/无票区分正确率 100%（在定义好的回放集内）；不符机场/日期/人数报价进入最低价的次数为 0。
50 次是开发验收下限，不能当作全国、全年真实准确率的统计证明。需要按平台和异常类型分别报告。

### M3：扩大覆盖，并回答“我能买到多少钱”

- 依次修去哪儿、同程、更多直营来源；每加一个来源必须通过独立的列表、产品、费用、资格、交接和变价回放。
- 会员/登录/App/支付条件作为显式可选条件，公开全价与本人可用价并列；不要求用户先填写所有账户资料才能搜索。
- 加入多成人、儿童/婴儿模型与对应规则，验证整单费用和库存是否满足人数；先完成模型再开放最低价承诺。
- 使用分来源并发、共享调用预算、熔断与缓存；登录态报价按用户隔离，不与匿名报价复用。
- 监控任务沿用相同全价政策。本人浏览器不在线时不能声称持续监控会员专属价格；提醒中明确监控的是公开价还是个人价。

验收：每个平台分别报告成功率、完整费用率、复核通过率、个人条件覆盖和调用成本；新增平台必须带来独立且可核价的增量。

### M4：在可靠报价上做更便宜的行程探索

- 去返程日期分别搜索，允许停留时长范围；附近机场显示额外交通费用与时间，未知交通费用不能默认 0。
- 比较联程与两张单程时保留独立出票、行李直挂、错失衔接与退改差异；用户可以排除这些方案。
- 用可解释的探索预算调度航线/日期/平台组合，披露实际搜索范围与未搜索范围。
- 价格历史只比较同口径、同商品条件的样本；历史最低不等于今天可以成交的最低。

验收：节省金额对应可复核产品；用时间、机场和出票差异解释代价。M2 未过之前不优先投入复杂日期矩阵和更多 AI 对话能力。

## 5. 前端验收要能反映搜索事实

| 场景 | 目标行为 |
| --- | --- |
| 开始操作 | 首步“解析出行需求”，确认条件后“开始比价”；需要登录的平台有明确入口 |
| 运行中 | 每来源显示排队、搜索、核价、需操作、超时或完成；取消后停止未发出的任务，丢弃过期查询响应 |
| 结果页 | 默认比较完整全价，单列待核候选；显示返回来源、完整全价来源、购买前复核来源三种不同计数 |
| 点击低价 | 明确人数、费用与条件；复核中防重复点击，有新价/缺票时先解释 |
| 无结果 | 区分没满足约束、来源失败、登录缺失和真的无票；支持只重试失败来源 |
| 键盘和手机 | 弹窗焦点循环/返回、Escape、触摸目标、金额不遮挡；表单与对话条件一致 |
| 动效 | 减少动态模式与玻璃降级正常；先录制低配 Windows 和手机的长任务、掉帧与列表交互，再定优化点 |

建议性能目标（尚未实测达标）：普通操作及时反馈，真实用户 INP 的第 75 百分位 ≤200ms；
搜索另记首条候选、首个全价、核价完成的 P50/P95，不用一个总耗时掩盖长尾。第三方等待与 Render 冷启动分开测量。

## 6. 指标、预算与停止条件

- 全价准确率：同产品复核总额一致次数 / 可做成对核价次数，同时报告无法复核和商品错配数量，不能通过丢弃失败样本美化结果。
- 完整覆盖率：取得完整费用证据的来源 / 本次计划的可用来源；另报来源实际成功返回率。
- 更便宜且可购买：相对基准节省金额，并附同条件复核证据；分公开价和本人条件价。
- 新鲜度：复核距展示/点击的时间、变价率与无票率。
- 成本：每个查询的接口次数、浏览器页数、额度消耗与耗时；预算按整次查询累计，缓存/重试也计入。

平台持续要求人工验证时暂停该来源并说明，不循环重试；预算耗尽就返回部分结果。
采集器页面结构改变时降低证据等级并阻止进入最低全价排序。测试使用脱敏固定回放，实时查询只用于受控验收，避免 CI 消耗真实接口配额。

## 7. 下一步完成的定义

接下来先交付 M1 的前两项：**报价证据契约与携程多产品采集**，并准备费用页回放样本。
第一阶段成功的演示应是一条用户自己的国内查询：能看见两个产品为什么价格不同，能读到真实机建燃油，能复核最低候选并准确交接。
只有这一闭环可重复运行后，才扩大到多个平台、多个旅客和复杂行程。

需要用户参与的场景仅集中在平台登录/验证，以及少量本人资格价的人工核对。密码、验证码和乘机人资料始终由用户直接在来源平台输入。
M1 的真实账号核验是主要外部依赖；在拿到样本前不承诺完成日期，也不把“先上线 UI”当作核价功能完成。
