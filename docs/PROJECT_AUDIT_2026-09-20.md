# Flight Lens 项目深度评估 · 2026-09-20

结论：保留现有液态玻璃前端与 contracts / domain / connectors 分层，优先重构报价证据、来源采集和购买前核价。项目已经能搜到部分真实报价，但尚不能可靠回答“国内各平台中，我现在实际能买到的最低价是多少”。本轮完成版本同步和一组可复现问题的修复；全网最低支付价仍是后续目标。

## 1. 范围与证据

- 液态玻璃版本已在原 Git 历史上提交到 `Rolling-Log/flight-lens` 的 `main`，初始同步提交为 `16b6cc607a32769180e433f28797174fa7e3a8c9`。使用现有已登录 GitHub CLI，无须重复安装连接器。
- 检查了前端表单、结果排序、弹窗、价格历史、账户、Edge Companion、API 编排、来源适配、领域约束、报价证据与 CI。
- Windows / Edge 实际页面检查；自动化使用独立的 3100 / 4100 端口和固定测试来源，不把测试票价混入用户正在使用的 3000 / 4000 服务。
- 国内实时样本：2026-09-20 02:42（北京时间），查询 **2026-10-20 PEK → SHA，单程，1 成人，经济舱，最多 1 次中转，无预算/行李限制**。这是单次观察，不是所有航线的成功率统计。
- 原始诊断与测试日志留在被 Git 忽略的 `work/local-preview/`；报告只保留必要摘要，不上传密钥、登录凭据和平台原始响应。

## 2. 国内搜票实测

修复 Windows 运行时之前，整次查询约 23.8 秒：

| 来源 | 本次结果 | 能否据此判断最低全价 |
| --- | --- | --- |
| 飞猪 FlyAI | `FLYAI_CLI_FAILED`，0 条 | 不能；之后确认 Node 25.3.0 的 libuv 断言崩溃。切换 Node 22.23.2 后，独立复测同航线返回 10 条真实列表报价 |
| 携程服务端浏览器 | `CTRIP_PAGE_CHANGED`，0 条 | 不能；不能把解析失败解释为无票 |
| 去哪儿服务端浏览器 | `QUNAR_PAGE_CHANGED`，0 条 | 不能；需结合实际登录/验证/页面结构继续诊断 |
| 同程服务端浏览器 | 30 条列表价 | 全部缺少税费证据；其中 16 条带机场冲突，不能替代指定 PEK → SHA 行程 |
| SerpApi / Google Flights | 4 条来源详情报价，最低观测金额 ¥720 | 项目标为 `detail_verified`，但这不是支付页核价，也不代表国内全平台最低 |

同程出现的 ¥350 列表价同时有机场冲突，不能拿它与 PEK → SHA 的 ¥720 来源全价直接比较。即便列表价对应机场正确，缺少税费时也只能作为待核价线索。

当前 `/health` 显示：来源配置 5 个，但数据库、账户认证、邮件和监控队列未配置。配置数是“启用了多少适配器”，不是“多少平台此刻能成功出价”。网页端航探账号也不是携程、去哪儿、同程或飞猪账号；服务器启动的隔离浏览器不会继承用户 Edge 登录态。

### 用户登录后的补充实测

用户加载扩展并登录携程后，03:03 的同条件查询得到：携程 Edge 30 条、同程 Edge 30 条、FlyAI 10 条、Google Flights 3 条，去哪儿仍解析失败。页面显示 4/5 个来源返回，18 个航班、31 个展示报价、42 个不符合条件的报价隐藏。携程和同程仍是列表价，说明登录已经接通，但费用明细采集尚未完成。

随后在携程实际展开 **2026-10-20 HU7601，07:45 PEK → 10:00 SHA**。列表价为 ¥550；航司直销产品显示托运行李 20kg；进入零额外服务的乘机信息填写页，页面明确列出 **票价 ¥550 + 机建 ¥50 + 燃油税 ¥70 = ¥670**。同一航班还有额外 ¥48 的服务包、其他加价产品与 16 个产品的展开入口。没有选择乘机人、点击“下一步”、提交订单或支付，因此此证据属于填写页费用观察，不是已成交价格。

这一实例直接支持下一阶段优先做运价产品展开与费用明细读取。它也说明不能因为当前聚合结果的“最低可核验全价”是另一航班的 ¥720，就认为全网没有更便宜的候选。上述 ¥670 是人工观察结果，本轮没有伪装成已自动采集的搜索结果。

## 4. 前端剩余不足

1. **价格口径混排。** 已标记待核验的列表价仍与来源核验价在一个列表内排序。应默认按完整全价比较，另设“可能更便宜、待核价”区域；用户能看见线索，但不会把 ¥350 票面价误当成 ¥350 可付款价。
2. **覆盖指标混淆响应与核验。** 当前 `success` 包括只返回列表价的同程，而部分文案叫“成功核验”。建议同时显示：返回结果来源数、完整全价来源数、支付前复核来源数、独立库存来源数。
3. **等待反馈不够具体。** 本机扩展全部返回后才发云端请求；百分比是固定阶段进度，虽然已有说明，仍不能表达哪个平台卡住、需登录还是无票。改为每来源状态、逐条结果更新、取消和只重试失败来源。
4. **对话输入的第一步不够直观。** 目前第一次“开始检索”只解析，随后确认再检索，这是现有设计且有测试。建议首次按钮改为“解析出行需求”，确认页明确展示将要搜索的条件。
5. **弹窗逻辑重复。** 来源、心选、账户、价格抽屉各自管理焦点、滚动和 Escape。共享动效已修复，但应统一成一个可访问弹窗基础组件，避免每处重犯同类问题。
6. **真实设备性能未量化。** 玻璃 SVG 位移、模糊与滚动导航较多，现有测试验证功能与降级，没有证明低配 Windows / 真机手机持续流畅。应测长任务、滚动掉帧、布局偏移与大量报价渲染，再决定减少何处特效。
7. **功能可用性提示。** 本地账户与监控后端尚未配置，入口不应让人误以为登录就能解锁 OTA 价格。价格提醒直接暴露 `ntfy Topic` 也不适合作为普通旅客最终流程。

本轮没有大范围重做视觉。现有布局、排序、收藏、来源详情、移动端适配、动效降级已具备继续开发的基础。

## 5. 搜索能力的根本缺口

### A. 定义“便宜”的对象

建议以同一用户、同一查询时刻、同一完整行程和条件下的 **最低可核验应付总额** 为目标：

`成人/儿童/婴儿票价 + 机建等税费 + 燃油 + 必选服务 + 满足要求的行李费用 − 已确认可用的即时优惠`

未知项不能视作 0；返现、积分抵扣、抽奖优惠不能直接混成无门槛公开价。还应保留机场、航段、舱等/运价产品、退改、人数、渠道、登录状态与优惠资格。当前只有成人模型，扩展到儿童/婴儿前需要更完整的旅客与税费规则。

### B. 获取稳定、完整的报价证据

- 携程、去哪儿当前实测解析失败，需用已登录 Edge 会话逐项复核。现有 Companion 是合理基础，但不是各平台都已经可用的证明。
- FlyAI 当前适配只读取 `ticketPrice / adultPrice`，不会自动获得所有卖家、机建燃油和支付优惠。
- DOM 采集最多 30 条，扩展最多 50 条；携程服务端只拿 `priceList[0]`，扩展只保留每航班的一个候选且当前只接单航段直飞响应。
- Google Flights 搜索最多取 4 个单程候选；往返最多展开 2 个去程、每个 3 个返程、最多 6 次报价详情请求。这是成本控制，不是完整最低价搜索。
- “新增很多适配器”需要与真实回归样本一起推进，否则只会增加失败来源数。航司直营也是独立核价基准，当前国内覆盖不能仅依靠 OTA 聚合。

### C. 机建燃油不能固定加一个常数

应先读来源税费明细；缺失时才使用有版本的规则估算，并保留“估算”状态。规则需要适用航司、出票生效日、航线范围/距离档、旅客类别、航段和豁免条件。

例如国航 2026-08-04 公告针对 8 月 5 日起销售的国内客票，成人燃油按距离分档为每航段 40 / 70 元，婴儿及部分旅客规则不同；国际票由系统计算。这说明规则必须带生效日期和适用范围，不能套给所有平台、航司和日期。[国航官方公告](https://www.airchina.com.cn/zh-CN/content/c/2026-08-04/30032.shtml)

本轮未建立全国机建/燃油规则数据库，也未将上述金额加入实际搜索结果。估算价不能升级成来源或支付核验价。

### D. 资格、运价产品和时效

- 目前带优惠资格的报价普遍排除出公开最低价，保护了公开比较，却无法回答“我这个老用户/会员究竟能买到多少”。需要可选择的个性化资格档案与实际适用证据。
- 当前按航段与卖家去重，缺少舱位运价产品、行李和退改条件的完整键，可能合并本应分开的商品。应枚举运价产品后，再按满足用户要求的总价选择。
- 缓存有披露，但用户停留后的报价陈旧、库存变化和优惠失效缺少购买前自动刷新闭环。应在跳转前重验最优的少量候选。
- 日期探测最多 15 个组合，往返日期一起平移，未覆盖不同停留时长；附近机场扩展也需拆清出发/到达语义、交通成本与可接受半径。
- 时区、跨日、中转停留、联程/分开出票风险和真实最低行李费用仍需专门的回放用例。当前部分页面适配会推断时长或机场，不能把推断当作来源事实。

### E. 必须有购买前核价反馈

建议证据状态为“列表线索 → 规则估算 → 来源明细 → 购买前确认”，每一步保留时间、金额分项、渠道、人数、资格和精确行程。项目已有人工 `price:verify` 留存入口，可复用，但还没有贯通所有来源的自动核价与精确商品跳转。

先从最便宜的 3～5 个候选展开详情，确认同一航班/运价产品和最终费用；用户点击前刷新。某平台失败则保留失败原因，最终结论写“本次已成功核验来源中的最低价”。任何支付都由用户在来源平台完成。

## 6. 推荐推进顺序与验收

以下指标是建议的验收目标，尚未达到。

| 阶段 | 具体工作 | 完成标准 |
| --- | --- | --- |
| 1：国内单程打通 | 先固定成人经济舱，打通携程、飞猪与一个航司直营的列表—详情—购买前金额链路；稳定 Windows 运行方式 | 建立 20 条国内航线样本，覆盖近/远期、两档距离、不同机场；所有展示分项有来源或明确估算标记 |
| 2：可比较全价 | 保存票面、机建、燃油、必选服务、行李、资格和时间；上线列表/估算/核验分层；增加支付前重验 | 在明确覆盖范围的人工样本中，以“分”为单位记录是否与来源最终应付金额一致；建议不少于 50 次核价，匹配率目标 ≥95%，缺失税费误判为 0 的次数必须为 0 |
| 3：增加平台与产品 | 加去哪儿、同程、更多航司；逐运价产品采集，正确去重；用户可选会员/优惠资格 | 每个平台独立报告成功率、全价完整率、重验变价率和相对直营价差；不能只按品牌数验收 |
| 4：最低价探索 | 分别探索去/返程日期与停留时长、附近机场、合法转机及拆单；并行渐进返回与预算控制 | 明确实际探索的组合数、未探索范围、成本和搜索时延；展示节省金额对应的时间/机场/出票风险 |

核心指标应是“最终价格匹配率、完整报价覆盖率、找到的更低价是否可购买、购买前变价率、搜索耗时和每次搜索成本”。页面打开率、来源配置数、抓到的最低数字都不能替代这些指标。

## 7. 验证与限制

- 本地 Node 22：类型检查、lint、165 项单元/集成测试、生产构建通过。
- Edge 桌面与移动视口：原 20 项 E2E 全部通过，另补同航班徽标归属的 2 项回归并通过，共 22 项。覆盖表单、键盘选择、弹窗焦点、排序、收藏、价格历史/提醒、账户视图与玻璃降级。
- 依赖审计：高危 0、严重 0；仍有 1 项中危，来自 Better Auth → drizzle-kit → 旧 esbuild 的可选依赖路径，尚未升级其完整兼容链。[esbuild 公告](https://github.com/advisories/GHSA-67mh-4wv8-2f99)
- 本轮同步与修复不等于已部署云端。尤其新的 `TRUSTED_PROXY_CIDRS` 需要部署环境验证，现有本地空配置适用于直接访问本机 API。[Fastify 安全公告](https://github.com/fastify/fastify/security/advisories/GHSA-3m5p-2c4r-xxw2)
- 用户已手动加载/重载扩展并登录携程，登录态实测单独记录；当前报告不声称已经完成个人账号优惠价或支付页核价。
- 本机升级后的开发模式出现 `Router action dispatched before initialization`，清理缓存后仍需复核；已采用生产构建预览继续验证。生产构建的交互测试通过不等于开发模式故障已定位。
