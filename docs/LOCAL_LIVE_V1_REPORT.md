# V1 本地真实检索报告

日期：2026-08-06
范围：只验证本地 V1，不进行 GitHub、Netlify、Railway 或 Neon 的线上变更。

## 结论

V1 可以合规地接入真实航班检索，但当前只能称为“单来源实时搜索”，不能称为“多来源比价”或“全网最低价”。本次验证使用已授权的 SerpApi Google Flights API，没有抓取 OTA 页面，没有混入 Sandbox 报价，也没有伪造第二来源。

本地完整链路已经成立：

1. 用户用自然语言输入条件；
2. 本地规则解析为统一 `SearchIntent`；
3. 真实 Fastify API 执行限流、Connector 调度和超时控制；
4. SerpApi Connector 检查免费账户和额度后请求 Google Flights 数据；
5. Domain 层按统一 Offer 口径过滤、排序并生成结论范围；
6. Web 页面展示来源状态、覆盖缺口、价格精度和审计状态。

因此，“真实检索”符合 V1 规范；“真实多来源比价”尚不符合，因为目前只有一个生产来源。

## 唯一一次真实查询

- 查询：`PVG -> NRT`
- 日期：`2026-09-05`
- 行程：单程
- 乘客：1 位成人
- 舱等：经济舱
- 灵活日期：关闭
- 附近机场：关闭
- Connector 重试：`0`
- Connector 缓存与失败陈旧回退：关闭
- 生产来源：仅 `SerpApi · Google Flights`
- 数据库：未配置

账户检查只读取状态和额度，没有输出 API Key。查询前后状态如下：

| 指标 | 查询前 | 查询后 | 变化 |
| --- | ---: | ---: | ---: |
| 方案 | 活动中的 0 美元方案 | 活动中的 0 美元方案 | 无 |
| 本月已用搜索额度 | 68 | 73 | +5 |
| 剩余额度 | 182 | 177 | -5 |

额度变化与代码上限完全一致：单程最多 1 次主搜索加 4 次 Booking Options 请求，共 5 次计费请求。往返路径的静态上限为 9 次；本次没有执行往返查询。

## 实际结果

真实请求完成了全链路提交，但原实现的 Booking Options 阶段没有在 20 秒 Connector 预算内返回。API 约 25 秒后以 `200` 返回结构化结果，来源报告为：

- `0/1` 个来源成功；
- `1` 个来源超时；
- `0` 个来源失败；
- `0` 个可比 Offer；
- 搜索审计未保存，因为本地没有配置数据库。

页面没有展示演示价或虚假最低价，而是明确显示“来源超时”“暂无”“本次计划检索 1 个来源”和“数据库尚未配置”。这证明失败披露链路可用，但也说明当时的真实结果稳定性尚未达到 V1 验收标准。

## 运行后修正

本次运行发现原实现使用 `Promise.all` 解析 Booking Options：只要该阶段整体超时，主搜索已经返回的真实航班、价格和 Google Flights 结果页也会被丢弃。

已在本地修正为：

- Booking Options 使用有界的 `Promise.allSettled`；
- 精确购买选项成功时仍优先使用精确卖方 Offer；
- 购买选项全部失败时，保留主搜索的真实航班与价格；
- 降级结果只允许跳转 Google Flights 搜索结果页，标记为 `search_results`；
- 明确附加 `SERPAPI_INITIAL_RESULTS_FALLBACK:SEARCH_RESULTS_HANDOFF_REQUIRES_REVALIDATION`；
- 部分 Booking Options 失败会记录失败数量；
- 没有合法 Google Flights URL 或完整价格/航段时仍然 fail closed。

该修正只通过离线固定响应测试验证。为遵守“一次受控真实搜索”的额度边界，本次没有再次调用真实航班搜索，因此不能把修正后的线上成功率写成已验证事实。

## V1 当前上限

本地 V1 现在可以做到：

- 真实单来源航班搜索；
- 真实来源健康和免费额度预检；
- 固定调用预算、零自动重试和本地请求限流；
- 统一 Offer、航段、总价、跳转精度与可比性模型；
- 精确 Offer 与搜索结果页降级的明确区分；
- 来源成功、空结果、失败、超时、缓存和重试的逐项披露；
- 无真实来源时绝不展示 Sandbox 价格；
- 完整的本地 Fastify/Web 端到端预览。

本地 V1 还不能做到：

- 真实多来源比价；
- 承诺全网最低价；
- 证明 SerpApi 在当前 20 秒预算内稳定返回精确购买选项；
- 持久化搜索审计和历史价格，因为 Neon 尚未配置；
- 验证 Railway、Netlify、Neon 的线上网络、CORS、密钥和迁移；
- 自动出票、支付或保证跳转后的库存与最终支付价。

## 验收判断

本次验证证明“真实数据链路可接通且产品能诚实处理失败”，并找到了一个会丢失真实主搜索结果的实现缺陷。修正后，代码层面的本地能力已达到单来源实时搜索候选版；但由于修正后的真实请求没有再次执行、生产来源仍只有一个、审计库未配置，不能把它标记为“真实比价 V1 已验收”。

进入线上部署前的下一道门槛是：在额度和授权允许时，用同一套受控参数验证一次修正后的真实降级/成功结果，再接入第二个合法生产 Connector，并在 Neon 中验证审计持久化。
